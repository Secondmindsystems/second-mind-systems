# Second Mind Systems

## Governed Repo — One Change. Two Gates. One Receipt.

**Governed Repo makes AI-assisted repository changes reviewable before trust is granted.**

AI can produce a technically valid change that still exceeds its task, touches the wrong files, or makes claims its evidence does not support. Governed Repo makes the proposed work, authority, paths, claims, decision, and evidence visible before that work is accepted.

**[Run the five-minute demo](https://github.com/Secondmindsystems/governed-change-demo)** · **[Inspect the evidence portfolio](https://github.com/Secondmindsystems/governed-ai-systems-portfolio)**

> The public demo proves deterministic evaluation of declared change snapshots and hash-linked receipt generation under fixed inputs and policies. It does not establish security, production readiness, live repository enforcement, customer validation, or execution authority.

## The problem it addresses

AI coding agents can move faster than traditional review practices. That creates practical questions:

- Was this work actually authorized?
- Did the proposed change stay inside the intended repository boundary?
- Are its claims supported by the available evidence?
- If it was blocked, can it be repaired without erasing what happened?
- Can a reviewer reproduce the decision and understand why it was made?

Governed Repo treats those questions as part of the engineering path, not as paperwork added after the change.

## How the public proof works

```text
An AI proposes a repository change
→ context and authority are checked
→ the Path Gate checks where it writes
→ the Claims Gate checks what it asserts
→ one fail-closed decision is produced
→ a governed receipt preserves what was checked and why
```

The included example begins with two independent failures and produces `BLOCK`. A bounded repair becomes a new revision, re-enters through the Context and Authority Precheck, reruns both gates, and produces `PASS`. The new receipt links to the earlier blocked receipt by ID and SHA-256 hash.

`PASS` means the declared snapshot passed the specific checks in the demonstration. It does not execute the change or grant broader authority.

- six strict JSON contracts;
- a Context and Authority Precheck;
- two independent policy gates;
- deterministic `BLOCK → repair → PASS` behavior;
- fail-closed `HOLD` and `BLOCK` cases;
- hash-linked governed receipts;

## Product map

| Part | Plain-English role | Current public status |
| --- | --- | --- |
| Proposed work | Describes the requested repository change before evaluation. | Represented by fixed public fixtures. |
| Context and Authority Precheck | Checks whether the proposal, authority, evidence state, source basis, policy versions, and required gates are ready for evaluation. | Runnable in the public demo. |
| Shared Change Envelope | Gives both gates the same versioned description of the proposed work. | Published as a strict JSON contract. |
| Path Gate | Checks repository-relative paths and operations against declared authority and path policy. | Runnable in the public demo. |
| Claims Gate | Checks whether declared claims have the required evidence, qualifiers, and limitations. | Runnable in the public demo. |
| Combined Decision | Produces one fail-closed `BLOCK`, `HOLD`, or `PASS` result. | Runnable in the public demo. |
| Governed Receipt | Records the inputs, policies, gate results, decision, and next lawful move. | Generated by the public demo. |
| Repair lineage | Preserves the earlier blocked decision when a repaired revision is evaluated. | Demonstrated with hash-linked receipts. |
| AI Protected Paths | Adds explicit local approval friction around designated files during the normal Git commit workflow. | Available as a bounded product today. |
| Surface | Helps pressure-test positioning, documentation, claims, and packaging during product review. | Advisory instrument only; it is not part of the public demo's deterministic enforcement path. |

The public demo is a standalone, inspectable evaluator. The wider Governed Repo MVP remains private and is not represented here as a publicly released runtime, live enforcement system, or production-qualified platform.

## What has and has not been demonstrated

### Demonstrated

- Deterministic evaluation for fixed fixtures, policies, evaluator versions, and evaluation time.
- Two materially different gates operating on one shared change envelope.
- Fail-closed CAP, path, claim, and evidence outcomes.
- A visible blocked revision followed by a bounded repaired revision.
- Receipt linkage that preserves the earlier decision.
- Clean-clone execution of the published instructions.
- Public evidence-packet integrity checking for the sanitized portfolio.
- Local Protected Paths behavior in the stated tested environments.

### Not demonstrated

- Production or deployment readiness.
- Security, tamper resistance, branch protection, or regulatory compliance.
- Live worktree inspection or automatic repository mutation by the public demo.
- Multi-agent, concurrent, high-scale, or adversarial robustness.
- Production performance, capacity, or latency characteristics.
- Customer adoption, market validation, or independent third-party validation.
- General authorization to execute any repository change.

## Protect sensitive files today

### AI Protected Paths

AI Protected Paths adds an explicit local approval step before normal Git commits can modify files you designate as sensitive.

It is designed for solo builders and small teams working with AI coding agents around files such as authentication, billing, infrastructure, migrations, prompts, governance, and release configuration.

The current release provides:

- configurable protected-file boundaries;
- an explicit local approval-token workflow;
- blocking on the normal Git pre-commit path when approval is absent;
- local proof receipts for hook-governed commit decisions; and
- Windows and tested-host macOS validation, with native Linux validation still pending.

[Get AI Protected Paths on Gumroad](https://secondmind.gumroad.com/l/aigtpg).

AI Protected Paths is local Git governance friction. It is not cryptographic or tamper-proof security, remote organization-wide enforcement, branch protection, or protection against `git commit --no-verify` or removal of the hook.
